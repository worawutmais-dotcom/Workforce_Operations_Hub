## 1. เป้าหมายรอบนี้

ทำให้ผู้ดูแลสามารถจัดการเวลาและออกสลิปได้จากลำดับเดียว โดยลดโอกาสจ่ายเงินจากข้อมูลที่ยังไม่ครบ

**Flow เป้าหมาย**

```text
Dashboard → รายการต้องตรวจ → Timesheet รายคน → ปรับรายการที่อนุญาต → ออกสลิป
```

สิ่งที่ไม่ทำในรอบนี้:

- เปลี่ยนกฎคำนวณค่าแรง, OT หรือ SSO
- ลบข้อมูล payroll / attendance เดิม
- เพิ่มระบบชำระเงินจริงหรือเปลี่ยนโครงสร้างฐานข้อมูลขนาดใหญ่
- ปรับ visual ทั้งระบบก่อนทดสอบ flow P0

## 3. Backlog ที่จะทำก่อน

### P0-A — Dashboard: คิวงานที่ต้องตัดสินใจ

**ปัญหา**
Dashboard แสดงข้อมูลดี แต่ผู้ใช้ยังต้องมองหาเองว่าควรแก้อะไรก่อน

**งาน**

1. เพิ่ม action queue ด้านบนสุดหลัง Live Shift Control
2. แสดงไม่เกิน 5 รายการ เรียงตามลำดับ:
   - เวลาเข้า/ออกไม่ครบ
   - OT รออนุมัติ
   - พนักงานที่ profile ขาดข้อมูลจำเป็น
   - Timesheet พร้อมตรวจเพื่อออกสลิป
3. ทุกแถวมีข้อมูล: ชื่อพนักงาน, เหตุ, วันที่, ผลกระทบ, CTA เดียว
4. CTA ต้องเปิด record ที่เกี่ยวข้องโดยตรง ไม่เปิดหน้าเปล่าหรือ modal ซ้อน

**Acceptance criteria**

- ผู้ใช้ไปจาก Dashboard ถึง Timesheet ที่ผิดปกติได้ภายใน 2 คลิก
- ไม่มี KPI ที่เป็น `0` ซ้ำหลาย card เมื่อไม่มีงานค้าง
- จำนวนใน action queue ตรงกับ endpoint ที่เป็นแหล่งข้อมูล

### P0-B — Attendance: Exception-first Excel ledger

**ปัญหา**
ตารางเวลาอ่านง่ายขึ้นแล้ว แต่ยังเปิดมาที่ “ทุกคน” ทำให้กรณีต้องตรวจหาได้ช้า

**งาน**

1. เพิ่ม preset filter: `ต้องตรวจ`, `วันนี้`, `ครบแล้ว`, `ทั้งหมด`
2. หากมีเวลาไม่ครบ ให้ตั้ง default เป็น `ต้องตรวจ`
3. ทำให้ปุ่มในแถวเป็น contextual action:
   - ไม่มีเช็กอิน → `ลงเวลาเข้า`
   - มีเช็กอินแต่ไม่มีเช็กเอาต์ → `ลงเวลาออก`
   - เวลาเต็ม → ซ่อน action อันตรายไว้ในเมนูเพิ่มเติม
4. เพิ่มคอลัมน์ `ผู้บันทึกล่าสุด` เมื่อ endpoint พร้อม โดยไม่จำลองข้อมูล

**Acceptance criteria**

- รายการลืมเช็กเอาต์มองเห็นโดยไม่ต้องกรองเอง
- ตารางรองรับ 100 แถวโดยหัวตารางยังอ่านได้และเลื่อนในพื้นที่ตาราง
- ทุก action อันตรายมี confirmation ที่บอกชื่อและวันที่

### P0-C — Payroll: Readiness ก่อนออกสลิป

**ปัญหา**
ผู้ใช้ต้องรู้ชัดว่าพนักงานคนใดออกสลิปได้ และติดตรงไหนหากยังไม่ได้

**งาน**

1. เพิ่ม badge ต่อแถว payroll:
   - `พร้อมออกสลิป`
   - `เวลาไม่ครบ`
   - `รออนุมัติ OT`
   - `ไม่มีเรตค่าจ้าง`
2. ปุ่มหลักต่อแถวเป็น `ตรวจ Timesheet` หรือ `ออกสลิป` ตามสถานะ
3. ใน Timesheet modal แสดงยอด: ฐาน, OT, เงินล่วงหน้า, SSO, หักอื่น, สุทธิ
4. เปลี่ยนข้อความทุกจุดที่อาจสื่อว่ามีการจ่ายเงินจริง เป็น `ยอดตาม Timesheet` หรือ `ประมาณการ`

**Acceptance criteria**

- ผู้ที่ `เวลาไม่ครบ` ไม่สามารถออกสลิปโดยไม่เห็นเหตุผล
- ยอดสุทธิใน preview และสลิปเท่ากันในกรณีทดสอบ
- สลิปแสดงชื่อพนักงานเป็นข้อมูลหลัก และ BVN ID เป็นข้อมูลรอง

## 5. UAT scenario ที่ต้องทำก่อน publish

ใช้ข้อมูลทดสอบอย่างน้อย 5 พนักงาน และห้ามเขียนทับข้อมูลการเงินจริง

| Scenario | ผู้ทดสอบ | ผลที่คาดหวัง |
|---|---|---|
| ลืมเช็กเอาต์ 1 คน | HR | ปรากฏใน Dashboard queue และ filter `ต้องตรวจ` |
| OT รออนุมัติ 1 รายการ | HR/Manager | Payroll ระบุว่า `รออนุมัติ OT` และยังไม่รวมยอด |
| OT อนุมัติแล้ว | Finance | Timesheet และ preview แสดงจำนวนชั่วโมง/อัตราพิเศษตรงกัน |
| เงินล่วงหน้า + SSO | Finance | รายการหักใน preview และสลิปเท่ากัน |
| สร้างสลิป | Finance | ชื่อพนักงาน, ช่วงงวด, ยอดสุทธิ และโลโก้ถูกต้อง |
| APK check-in/out | พนักงานทดสอบ | เวลาบนเครื่องและระบบตรง Bangkok, GPS status อ่านง่าย |

## 6. Quality gate

ก่อน commit:

```text
node tools/admin_redesign_contract_test.mjs
node tools/ot_multiplier_test.mjs
node tools/shortfall_policy_test.mjs
git diff --check
```

ก่อนส่ง APK (เมื่อมีการแก้ mobile):

```text
C:\flutter\bin\flutter.bat test
C:\flutter\bin\flutter.bat analyze
C:\flutter\bin\flutter.bat build apk --release
```

ก่อน publish:

1. ตรวจ review เปรียบเทียบ preview กับสลิปอย่างน้อย 1 รายการต่อประเภทค่าจ้าง
2. ยืนยันว่า endpoint `swift-handler` เป็นเวอร์ชันที่รองรับ action ใหม่
3. Publish `admin_codex/index.html` ตามช่องทาง host ที่ใช้งานจริง
4. บันทึก commit, URL/เวอร์ชันที่ deploy และผล UAT

## 7. ความเสี่ยงและวิธีควบคุม

| ความเสี่ยง | วิธีควบคุม |
|---|---|
| เปลี่ยน UI แล้วสื่อว่าเงินถูกจ่ายจริง | ใช้คำว่า `ตาม Timesheet` / `ประมาณการ` จนกว่าจะมี payment record ที่ตรวจสอบได้ |
| ปรับ CSS กระทบ mobile | ตรวจ viewport desktop และ mobile; mobile action ต้องไม่เล็กกว่า 40px |
| API ยังไม่ส่ง field สำหรับ readiness | แสดงสถานะที่พิสูจน์ได้เท่านั้น และไม่เดาข้อมูล |
| UAT ใช้ข้อมูลจริง | ใช้บัญชี/งวดทดสอบ หรือสำรองข้อมูลก่อนตามกระบวนการ |
| Publish Admin กับ backend คนละเวอร์ชัน | ตรวจ capability endpoint และทดสอบ action สำคัญหลัง publish |

## 8. Definition of Done

รอบนี้ถือว่าเสร็จเมื่อ:

- P0-A, P0-B และ P0-C ผ่าน acceptance criteria
- test ตาม Quality gate ผ่าน
- HR และ Finance ทำ UAT scenario ที่เกี่ยวข้องและลงผล
- ไม่มีการเปลี่ยนกฎคำนวณเงินโดยไม่ได้รับอนุมัติ
- commit, release note และสถานะ deploy ถูกบันทึกชัดเจน

## 9. ผลการดำเนินงานรอบพัฒนา

### ส่งมอบแล้วในโค้ด

- Dashboard มีคิวงานสูงสุด 5 รายการ เรียง `เวลาไม่ครบ → OT รออนุมัติ → ข้อมูลเอกสารพนักงาน → คำขอลา → ออกสลิป`
- คิวงานแสดงชื่อพนักงาน สาเหตุ และปุ่มเดียวที่พาไปหน้าปฏิบัติการที่เกี่ยวข้อง
- ตารางบันทึกเวลาเปิดที่ `ต้องตรวจ` เมื่อพบรายการค้าง และมีตัวกรอง `วันนี้`, `ครบแล้ว`, `ทั้งหมด`
- ปุ่มยกเลิกบันทึกถูกย้ายไปเมนูรายการ เพื่อลดโอกาสลบข้อมูลโดยไม่ตั้งใจ
- Payroll แสดงสถานะรายพนักงานจากข้อมูลจริง: `พร้อมออกสลิป`, `เวลาไม่ครบ`, `OT รออนุมัติ`, `ยังไม่ตั้งเรต`
- แถวที่ออกสลิปได้เปิด Timesheet ก่อนเข้าสู่หน้าตรวจสลิป ส่วนแถวที่ยังไม่พร้อมพาไปแก้สาเหตุที่ถูกต้อง
- หน้าตั้งค่าการจ่ายเงินเดือนแสดงผลกระทบก่อนบันทึก: จำนวนพนักงานที่ใช้งาน, วันทำงานต่อสัปดาห์, สถานะ SSO และนโยบายไม่ครบกะ
- Payroll มีคิว `ตรวจสลิปที่พร้อม` ซึ่งรวมเฉพาะผู้ที่ผ่านเงื่อนไข แล้วให้ตรวจ/ออกสลิปทีละคนก่อนพิมพ์
