# BVN Workforce Hub — UX/UI Product Audit

วันที่: 18 พฤศจิกายน 2569  
ขอบเขต: Admin Console และ Employee APK รุ่น `1.0.14+14`  
หลักฐาน: โค้ดปัจจุบันและภาพหน้าจอที่ผู้ใช้ส่งมา ไม่ใช่การทดสอบ UAT ด้วยบัญชีจริง

## บทสรุปสำหรับผู้บริหาร

ระบบมีแกนธุรกิจที่ถูกต้องแล้ว: เวลาเข้า–ออก → Timesheet → เงินเดือน → สลิป แต่ UI ยังมีร่องรอยจากการเพิ่มหน้าจอหลายรอบ ทำให้บางหน้าเป็นทั้ง dashboard, form และ report พร้อมกัน ผู้ใช้จึงเห็นตัวเลขมากกว่างานที่ต้องตัดสินใจ

ทิศทางที่แนะนำคือ **“ควบคุมงานจากข้อยกเว้น แล้วออกเอกสารจากข้อมูลที่ตรวจแล้ว”** ไม่ใช่ “เปิดหน้าแล้วไล่หาปุ่ม”

- Dashboard มีหน้าที่บอกว่าใครหรือรายการใดต้องจัดการก่อน
- บันทึกเวลาเป็น Excel-like ledger สำหรับแก้ข้อยกเว้นอย่างรวดเร็ว
- เงินเดือนเป็น workspace สำหรับตรวจ Timesheet รายคนและออกสลิปเท่านั้น
- การตั้งค่าแยกตามผลกระทบ ไม่รวมเป็นถังเดียว
- APK มีหน้าที่เดียว: พนักงานเช็กอิน/เช็กเอาต์ เห็นกะและสถานะพื้นที่ได้ทันที

## Product direction

| มิติ | ทิศทาง |
|---|---|
| Product | เครื่องมือปฏิบัติการพนักงานสำหรับ HR, ผู้จัดการ และการเงิน ที่ต้องเชื่อถือข้อมูลเวลาและสลิปได้ |
| Character | สุขุม, แม่นยำ, รับผิดชอบ |
| World | สมุดลงเวลา, แฟ้มเงินเดือน และเครื่องมือควบคุมกะงาน |
| Moment | Live Shift Control บน Dashboard และ Timesheet ก่อนออกสลิป |
| Signature | จุดสถานะเล็กที่สื่อความหมายจริง เช่น พร้อม, ต้องตรวจ, รออนุมัติ |

## วิจารณ์แบบตรงไปตรงมา

1. **Dashboard ดีขึ้นแต่ยังพยายามบอกทุกเรื่องพร้อมกัน** — Live Shift Control เด่นแล้ว แต่ KPI, ตารางทีม, แนวโน้มรายบุคคล, จุดเช็กอิน และปฏิทินยังแข่งขันกัน ความสำคัญต้องเรียงตามสิ่งที่ทำให้จ่ายเงิน/ทำงานผิด
2. **คำว่า “ยอดสุทธิ” เสี่ยงถูกตีความเป็นยอดที่จ่ายแล้ว** — ทุกจุดที่มาจาก preview ต้องมีคำว่า “ตาม Timesheet” หรือ “ประมาณการ” จนกว่าจะมีโมดูลการชำระเงินจริงที่ตรวจสอบได้
3. **เวลาทำงานควรเป็น exception-first** — ตารางแบบ Excel เหมาะกับการลงข้อมูลมาก แต่ควรเปิดด้วย filter `ต้องตรวจ` เมื่อมีข้อมูลค้าง ไม่ใช่ `ทุกคน` เสมอ
4. **เงินเดือนต้องไม่ซ่อนที่มาของยอด** — ผู้ใช้ต้องเปิด Timesheet ได้ในคลิกเดียวจากทุกแถว และสลิปต้องออกจากข้อมูลเดียวกับที่เห็น ไม่ใช่ snapshot คนละชุด
5. **ตั้งค่ายังมีความเสี่ยงสูง** — ค่าเวลางาน, SSO, OT, จุดเช็กอิน และบัญชี Admin มีผลกระทบคนละระดับ จึงต้องแยกส่วนและมีข้อความ “มีผลเมื่อใด/กระทบใครบ้าง”
6. **APK ยังมีพื้นที่ข้อมูลซ้ำ** — กะวันนี้, เวลาเช็กอิน, แผนที่ และปุ่มเช็กเอาต์ต้องเรียงเป็นลำดับการตัดสินใจ ไม่ใช่ card ขนาดใกล้กันทั้งหมด

## ข้อเสนอรายหน้าหลังบ้าน

### 1. Dashboard

**บทบาทที่ถูกต้อง:** หน้าตัดสินใจ ไม่ใช่รายงานรวมทุกอย่าง

- ให้ Live Shift Control เป็น visual หลักหนึ่งเดียว
- ด้านล่างให้มี `งานที่ต้องทำก่อน` ก่อนรายชื่อทีมเสมอ
- ย้าย “แนวโน้มรายบุคคล” และ “จุดเช็กอิน” ไว้หลังปฏิทินหรือทำเป็น collapse เมื่อไม่มีข้อยกเว้น
- ปฏิทินทีมต้องตอบได้ใน 1 คลิกว่า วันใดมีใครขาด/สาย/เวลาไม่ครบ และเปิดรายละเอียดวันนั้นได้
- ไม่ควรมี KPI ค่า `0` หลายกล่องเมื่อไม่มี action; เปลี่ยนเป็นข้อความ “ไม่มีรายการค้าง” หนึ่งพื้นที่

### 2. บันทึกเวลา

**บทบาทที่ถูกต้อง:** Excel ledger สำหรับแก้ข้อยกเว้นโดยเร็ว

- ตารางปัจจุบันควรคงแนวทาง grid, header ตรึง, ตัวเลขชิดขวา และแถวสลับสี
- เพิ่มคอลัมน์ `แก้ล่าสุดโดย` และ `แหล่งที่มา` เมื่อ backend รองรับ เพื่อแยกพนักงานบันทึกเองกับ Admin ลงแทน
- ปุ่มระดับแถว: แสดงเพียง action ที่ทำได้ เช่น “ลงเวลาออก” เมื่อขาดออก; ซ่อน “ยกเลิก” ไว้ในเมนูเพิ่มเติมสำหรับข้อมูลครบ
- บนมือถือรักษา touch target อย่างน้อย 40px แม้ desktop จะใช้ปุ่ม 22–28px

### 3. บุคคลและอนุมัติ

**บทบาทที่ถูกต้อง:** ทะเบียนเดียว + inbox งานคน

- แถวรายชื่อควรอ่านจบในบรรทัด: ชื่อ, BVN ID, ตำแหน่ง, สถานะ, งานค้าง
- คิวอนุมัติเรียงตาม deadline และ financial impact ไม่ใช่ตามชนิดคำขอ
- เลขบัตรและโทรศัพท์เต็มแสดงเฉพาะใน profile detail หลังยืนยันสิทธิ์
- แยก action อันตราย เช่น ปิดใช้งาน/ลบ/รีเซ็ตรหัส ออกจาก action ปกติด้วย menu ที่มี confirm ชัดเจน

### 4. เงินเดือนและสลิป

**บทบาทที่ถูกต้อง:** workspace ตรวจหลักฐานและออกเอกสาร

- Flow ปัจจุบันที่ต้องยึด: `เลือกงวด → ตรวจ Timesheet → ปรับรายการ → ออกสลิป`
- ไม่แสดง `ล็อกงวด` หรือ `บันทึกจ่าย` เป็นขั้นตอนหลัก เพราะไม่ได้เป็นกระบวนการที่ผู้ใช้ต้องทำก่อนออกสลิป
- สลิปต้องใช้ชื่อพนักงานเป็นข้อมูลหลัก; BVN ID เป็นข้อมูลรอง
- ก่อนพิมพ์ให้มี preview ที่ชี้ชัด: รายได้ปกติ, OT ที่อนุมัติ, เงินล่วงหน้า, SSO, หักอื่น, สุทธิ
- ถ้ามีการแก้รายการหัก ให้แสดงผู้แก้และเวลาที่แก้ใน Timesheet/preview

### 5. ตั้งค่า

**บทบาทที่ถูกต้อง:** พื้นที่ตั้ง policy ที่รู้ผลกระทบก่อนกดบันทึก

- แบ่งเป็น 4 cards ตาม architecture ด้านบน ไม่ใช้หน้า form ยาว
- Setting ที่มีผลกับเงินต้องมี effective date และ confirmation ที่กล่าวผลกระทบ
- เก็บ endpoint/technical configuration ใน developer-only section ที่ role จำกัด

## มาตรฐาน UI ที่ต้องรักษา

- Desktop ใช้ 4px rhythm; compact action 28px; ปุ่มในตาราง 22–28px
- Mobile ห้ามต่ำกว่า 40px สำหรับ action ที่ผู้ใช้กดด้วยนิ้ว
- สีแบรนด์ navy ใช้เฉพาะ primary action และ document emphasis
- สี semantic: เขียว = พร้อม/ครบ, amber = ต้องตรวจ, แดง = ข้อผิดพลาด/การทำลายข้อมูล, เทา = ยังไม่ถึง/ไม่เกี่ยวข้อง
- ตัวเลขเวลาหรือเงินใช้ `tabular-nums` และจัดชิดขวา
- หนึ่งพื้นที่มี primary CTA ได้เพียงหนึ่งปุ่ม; action รองใช้ outline/quiet control
- ไม่มี gradient, glow, emoji decoration หรือ KPI ที่คลิกไม่ได้โดยไม่มีเหตุผล

## ตัวชี้วัดหลังปรับ

| Metric | เป้าหมายเริ่มต้น |
|---|---|
| เวลาจาก Dashboard ถึงรายการเวลาไม่ครบ | ไม่เกิน 2 คลิก |
| Timesheet ที่ต้องตรวจแต่ถูกออกสลิป | 0 รายการ |
| ความต่างยอด preview กับสลิป | 0 บาท |
| งานอนุมัติค้างเกิน SLA | ลดลงทุกเดือน |
| การลงเวลาแทนผิดพนักงาน/ผิดวัน | 0 รายการใน UAT |
| อัตราพนักงานที่เช็กเอาต์ครบ | ติดตามรายสัปดาห์และเพิ่มขึ้น |

## แผนตรวจรับ

1. UAT ด้วยข้อมูลทดสอบอย่างน้อย 5 พนักงาน, 2 รอบจ่าย, มี OT, เวลาไม่ครบ, ลา, เงินล่วงหน้า และ SSO
2. ให้ HR ทำ 3 งาน: หาเวลาไม่ครบ, อนุมัติ OT, ออกสลิป 1 คน แล้วจับเวลาและบันทึกจุดติดขัด
3. ให้ Finance เทียบ Timesheet → preview → สลิปทุกบรรทัดก่อนอนุมัติใช้งานจริง
4. ให้พนักงานทดสอบ APK บนอุปกรณ์จริงทั้ง UTC boundary, GPS ใน/นอกพื้นที่ และ check-out
