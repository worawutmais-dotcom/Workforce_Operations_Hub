# BVN Admin Console — UX/UI review

วันที่ประเมิน: 16 พฤศจิกายน 2569 · ขอบเขต: หน้าจอหลังบ้านปัจจุบัน

## Direction

- **Product:** คอนโซลสำหรับผู้จัดการร้าน/บริษัทที่ต้องจัดการคน เวลา และเงินเดือนโดยตรวจสอบย้อนหลังได้
- **Character:** สุขุม, แม่นยำ, รับผิดชอบ
- **World:** สมุดลงเวลาและแฟ้มเงินเดือนที่จัดระเบียบบนโต๊ะทำงาน
- **Moments:** แถวพนักงานที่อ่านจบในบรรทัดเดียว และ Timesheet ก่อนล็อกงวด
- **Signature:** จุดสถานะเล็ก ๆ ที่หมายถึงงานต้องตัดสินใจ ไม่ใช้สีเป็นของตกแต่ง

## ข้อวิจารณ์ตรงไปตรงมา

1. ระบบเคยพยายามทำทุกอย่างให้เห็นในหน้าเดียว จึงเกิด card ซ้อน, แถบสีมากเกิน และปุ่มความสำคัญเท่ากัน ผู้ใช้ไม่รู้ว่าจะเริ่มตรงไหน
2. เมนูเดิมแยก “พนักงาน”, “อนุมัติ”, “เวลางาน” ทั้งที่การตัดสินใจจริงต้องทำต่อเนื่องกัน ทำให้ต้องสลับหน้าจอบ่อย
3. เงินเดือนเป็นหน้าที่เสี่ยงที่สุด แต่เดิมข้ามจากยอดรวมไปพิมพ์สลิปได้เร็วเกินไป จึงต้องมี Timesheet และสถานะก่อนล็อกงวด
4. ข้อมูลส่วนบุคคลไม่ควรถูกนำมาแสดงเต็มเลขในตารางหลัก และไม่ควรให้ APK เขียนทับทะเบียนโดยตรง
5. `employees` และ `approvals` หน้าเก่ายังเข้าถึงผ่าน deep-link ได้ แม้เมนูหลักรวมเป็น “บุคคล & อนุมัติ” แล้ว ควรถอดเมื่อยืนยันว่าไม่มี bookmark ใช้งาน

### Redline รายหน้าที่ต้องทำให้จบ

#### วันนี้

- **แย่:** เป็น dashboard ที่พยายามเป็นทั้งศูนย์เตือน, สรุปทีม, สรุปเงินเดือน และทางลัด จึงกลับไปมี KPI ซ้ำ แม้ไม่มีสิ่งใดต้องทำ
- **ควรเหลือ:** งานที่ต้องตัดสินใจ 3 ประเภทเท่านั้น: เวลาไม่ครบ, คำขอรออนุมัติ, และงวดเงินเดือนที่ยังไม่พร้อม
- **ควรลบ:** การ์ดสรุปที่กดต่อไม่ได้ และค่า `0` หลายกล่องในวันที่ไม่มีข้อมูล
- **รูปแบบที่ถูกต้อง:** แถบ “ต้องทำวันนี้” เป็นรายการเรียงตามความเสี่ยง แล้วตามด้วยตารางทีมขนาดกะทัดรัด 1 แถวต่อคน

#### เวลาทำงาน

- **แย่:** ตารางเวลา, เช็กอินแทน, GPS และประวัติ ถูกวางเป็นงานชนิดเดียวกัน ทั้งที่ผู้ดูแลมองหา “รายการผิดปกติ” ก่อน
- **ควรเพิ่ม:** มุมมอง exception-first: เวลาเข้า/ออกขาด, อยู่นอกพื้นที่, และแก้ไขย้อนหลัง อยู่บนสุด พร้อมปุ่ม “ลงเวลาแทน” ในแถวของคนนั้น
- **ควรลบ:** ปุ่มลงเวลาแทนที่ลอยอยู่โดยไม่ผูกกับพนักงาน/วันที่ เพราะเพิ่มโอกาสบันทึกผิดคน
- **ข้อมูลที่ต้องเห็นทุกแถว:** พนักงาน, วันที่, เข้า, ออก, ชั่วโมง, สถานะ, ผู้แก้ล่าสุด

#### บุคคล & อนุมัติ

- **แย่:** รางรายชื่อและคิวอนุมัติอยู่ร่วมหน้าได้ถูกทางแล้ว แต่ยังมี icon และเมนูสามจุดมากกว่าที่ผู้ใช้ต้องใช้จริง และคำขอแต่ละชนิดให้ความสำคัญเท่ากัน
- **ควรรวม:** คำขอข้อมูลส่วนตัว, รีเซ็ตรหัสผ่าน, ลา, OT, แก้เวลา, เงินล่วงหน้า เป็น “งานค้างของพนักงาน” หนึ่งแถว แยกด้วย filter ไม่ใช่แยกหน้าจอ
- **ควรเพิ่ม:** แถวทะเบียนที่อ่านใน 1 บรรทัด: ชื่อ · รหัส BVN · ตำแหน่ง · โทรศัพท์ที่ปกปิดบางส่วน · สถานะ · งานค้าง · เมนูเดียว
- **ข้อมูลอ่อนไหว:** เลขบัตรเต็มแสดงเฉพาะในรายละเอียด/ตอนอนุมัติ ไม่แสดงใน list, export หรือ API list ปกติ

#### เงินเดือน

- **แย่:** หน้าเงินเดือนที่สรุปยอดก่อนพิสูจน์แหล่งที่มา ทำให้ผู้ใช้เชื่อยอดโดยไม่เห็นว่าเวลาหรือ OT ครบหรือไม่
- **ควรเปลี่ยน:** ให้ Timesheet เป็นด่านแรก: แถวพนักงานต้องมี “พร้อมออกสลิป / ต้องตรวจ” และเปิดดูวัน, เวลา, OT, ×N, หักเงินได้ก่อน
- **ควรลบ:** ปุ่มล็อกงวดหรือพิมพ์สลิปที่อยู่ระดับเดียวกับปุ่มตรวจรายการ
- **ควรเพิ่ม:** สถานะ 4 ค่าเท่านั้น: `พร้อม`, `เวลาไม่ครบ`, `รออนุมัติ`, `ถูกล็อก`; และปุ่ม “ล็อกงวด” ต้อง disabled พร้อมเหตุผลเมื่อยังไม่พร้อม

#### เงินล่วงหน้า

- **แย่:** เป็นหน้าที่แยกจากผลกระทบใน payroll จึงทำให้อนุมัติแล้วลืมว่าระบบจะหักเมื่อไร
- **ควรเปลี่ยน:** ในแต่ละรายการบอกยอดคงเหลือ, งวดที่จะเริ่มหัก, และผลกระทบสุทธิของงวดปัจจุบัน
- **ควรเพิ่ม:** filter `รออนุมัติ / รอจ่าย / กำลังหัก / ปิดแล้ว` และไม่ใช้สีเดียวแทนสถานะทั้งหมด

#### ค่าจ้างและ OT

- **แย่:** กติกาบริษัท, กติกาเฉพาะคน, วันหยุด และตัวคูณอยู่ใกล้กันเกินไป ผู้ใช้แยกไม่ออกว่าแก้ค่าไหนกระทบทั้งบริษัท
- **ควรแยก:** 1) มาตรฐานบริษัท 2) ข้อยกเว้นรายพนักงาน 3) ปฏิทินวันหยุด/×N
- **ควรเพิ่ม:** ทุก save แสดง preview ผลกระทบ เช่น “มีผลกับ 18 คน ตั้งแต่งวด ธ.ค. 2569” ก่อนยืนยัน
- **ควรลบ:** ค่า default ที่ดูเหมือนเปิดใช้แล้วโดยยังไม่ได้บันทึกจริง

#### ใบแจ้งหนี้ลูกค้า

- **แย่:** การตั้งหัวบิล/โลโก้เคยอยู่ห่างจากเอกสารที่พิมพ์ จึงไม่รู้ว่าการอัปโหลดสำเร็จจริงหรือไม่
- **ควรเปลี่ยน:** sidebar ซ้ายเป็นรายการใบแจ้งหนี้, พื้นที่หลักเป็น preview A4 ที่มีโลโก้จริงและปุ่ม “แก้หัวบิล” เดียว
- **ควรเพิ่ม:** preview ก่อนออก PDF, สถานะ draft/issued/paid/overdue, และบันทึกการเปลี่ยนโลโก้

#### ตั้งค่า

- **แย่ที่สุดของหลังบ้าน:** เป็นถังรวมการตั้งค่าที่เกี่ยวกับความปลอดภัย, บริษัท, การเงิน, ตารางงาน และการเชื่อมต่อ ผู้ใช้ไม่รู้ว่าการแก้ช่องหนึ่งเสี่ยงแค่ไหน
- **ต้องแยก 4 กลุ่ม:** บริษัทและเอกสาร, เวลางานและพื้นที่, ค่าจ้างและวันหยุด, ผู้ดูแลและความปลอดภัย
- **ควรลบ:** Endpoint และข้อมูลเทคนิคจากหน้าการตั้งค่าสำหรับผู้ปฏิบัติงานทั่วไป; อยู่ในส่วน developer-only
- **ควรเพิ่ม:** `บันทึกแล้ว`, ผู้แก้ล่าสุด, เวลาเริ่มมีผล, และ rollback ของค่ากติกา

#### บันทึกการใช้งาน

- **แย่:** ตาราง log ดิบทำให้ค้นหาว่าใครแก้เงินเดือนหรือข้อมูลบัตรไม่ได้
- **ควรเปลี่ยน:** event feed ที่ filter ได้ตาม คน / ประเภทรายการ / ช่วงเวลา พร้อมลิงก์กลับไปยัง record
- **ควรเพิ่ม:** event สำคัญต้องเห็น before → after เช่น ปรับ ×N จาก 1.5 เป็น 2.0 และผู้กระทำ

### Redline APK

#### เข้าสู่ระบบ

- ใช้คำว่า `รหัสพนักงาน BVN-XXXX` ไม่ใช่คำกำกวม เช่น “รหัสพนักงาน” อย่างเดียว
- มีลิงก์ “ลืมรหัสผ่าน” ที่ส่งคำขอให้ Admin แทนการบอกให้พนักงานโทรถามเอง
- ไม่แสดง Device token, URL, หรือข้อความโหมดทดสอบใน flow ปกติ

#### วันนี้ / เช็กอิน

- **แย่:** ผู้ใช้ต้องอ่านการ์ดเวลา, tile เข้า/ออก, แผนที่, banner ยืนยัน และปุ่มใหญ่หลายระดับ เพื่อทำงานเพียง “เช็กอิน”
- **ลำดับที่ถูกต้อง:** สถานะงานวันนี้ → เวลาเริ่ม/เลิกจาก backend → สถานะ GPS แบบ 1 ประโยค → แผนที่ → CTA เดียว
- **แผนที่:** ทำหน้าที่ “หลักฐานพื้นที่” ไม่ใช่ตัวควบคุม จึง zoom เข้า/ออกได้ แต่ลากตำแหน่งไม่ได้; marker เล็ก, วงรัศมีโปร่ง, ป้ายสถานะอยู่ด้านล่าง
- **ห้าม:** ให้หน้าบอกว่า “ไม่มีข้อมูล/ซิงค์ไม่สำเร็จ” แต่แสดงสถานะ `เสร็จงานแล้ว` เพราะเป็นคำที่ขัดแย้งกัน
- **CTA:** แสดงเพียงปุ่มที่ทำได้ตอนนั้น: ก่อนเข้า = เช็กอิน, หลังเข้า = เช็กเอาต์, นอกพื้นที่ = ปุ่ม disabled พร้อมระยะห่างและปุ่ม refresh GPS

#### เวลางาน / ปฏิทิน

- **แย่:** สีชมพู/ฟ้า/เทาและ ×2 มองเหมือน dashboard เกม ไม่เหมือนบัญชีเวลางาน และ ×2 ไปขึ้นวันผิดทำลายความเชื่อถือทันที
- **ควรเปลี่ยน:** ปฏิทินเป็น neutral 90%; ใช้จุดเล็กสำหรับสถานะ, สีแดงเฉพาะ “ต้องแก้”, สีเขียวเฉพาะ “ครบ”, สีทองเฉพาะ “วันค่าจ้างพิเศษ”
- **รายละเอียดวัน:** แสดง `กะ 08:30–17:30`, เข้า, ออก, ชั่วโมง, สถานะ และ `ตัวคูณค่าจ้าง ×N` โดยระบุที่มาจากหลังบ้าน เช่น `วันหยุดบริษัท`
- **ต้องแก้เชิงระบบ:** ค่า shift, วันทำงาน, วันหยุด, ×N ต้องถูกส่งจาก Edge Function ชุดเดียวกับ payroll; ห้ามมี fallback ที่สร้างกฎใน APK เอง

#### ลางาน

- หน้าฟอร์มต้องเริ่มด้วยสิทธิคงเหลือและวันหยุดที่ทับซ้อนก่อน เลือกประเภท/วันที่ทีหลัง
- ใช้ preview สั้น “ใช้ 2 วัน · คงเหลือ 4 วัน” ก่อนส่ง และแจ้งผู้อนุมัติ/สถานะหลังส่ง

#### คำขอ

- รวมคำขอลา, แก้เวลา, รีเซ็ตรหัสเป็น timeline เดียว แสดง `รอผู้จัดการ`, `อนุมัติแล้ว`, `ต้องแก้ไข` ไม่ใช่แค่สี
- เมื่อถูกปฏิเสธต้องแสดงเหตุผลและปุ่มแก้ไข/ส่งใหม่ตรงรายการ

#### บัญชี

- แยกหัวข้อ “ข้อมูลส่วนตัว”, “ความปลอดภัย”, “ช่วยเหลือ” เป็น 3 section
- การส่งเลขบัตร/โทรศัพท์ใช้คำขอรอตรวจทาน (ที่เพิ่มแล้ว) และบอกชัดว่า Admin จะอนุมัติก่อนใช้ในทะเบียน
- ไม่แสดงเลขบัตรเต็มหลังส่ง; แสดงเพียง 4 หลักท้ายและสถานะคำขอ

## ตรวจแบบผู้ใช้งานหลังบ้าน — 17 พฤศจิกายน 2569

### ข้อวิจารณ์ตรงไปตรงมา

1. **เมนูพนักงานซ้ำกันจนไม่รู้ว่าต้องทำที่ใด** — เดิมมีทั้ง “บุคคล & อนุมัติ”, “พนักงาน” และ “งานรออนุมัติ” ทั้งที่เป็นงานต่อเนื่องเดียวกัน. ผู้ใช้ต้องจำว่าคำขออยู่หน้าไหน และเสี่ยงกลับไปแก้ข้อมูลคนละบริบท.
2. **หน้าวันนี้ควรตอบคำถาม ไม่ใช่แข่งกันแสดงบัตร** — ผู้ดูแลต้องเห็นก่อนว่าใครยังไม่เข้า, ใครสาย, และอะไรต้องอนุมัติ; ตัวเลขที่กดต่อไม่ได้ควรถอยไปเป็นข้อมูลรอง.
3. **การลงเวลาแทนต้องไม่เปลี่ยนจอเองขณะกำลังกรอก** — polling บนหน้าที่เป็นแบบฟอร์มเสี่ยงรีเซ็ต selection หรือทำให้เข้าใจว่าข้อมูลถูกบันทึกแล้ว. การรีเฟรชสดควรมีเฉพาะหน้าติดตามสถานะ.
4. **การวิเคราะห์ต้องพาไปสู่รายการจริง** — สรุปรายเดือนรายคนในหน้า วันนี้ควรเปิดปฏิทินและวันผิดปกติของคนนั้นได้ทันที ไม่ควรเป็นกราฟสวยแต่แก้ไขอะไรไม่ได้.

### สิ่งที่แก้ในรอบนี้

- ยุบเส้นทาง “พนักงาน” และ “งานรออนุมัติ” เข้าสู่ **บุคคล & อนุมัติ** ซึ่งเป็น workspace เดียวสำหรับทะเบียนและการตัดสินใจ. Bookmark เก่าทั้งสองเส้นทางจะ redirect มาหน้าเดียวกัน.
- เก็บการรีเฟรชอัตโนมัติไว้เฉพาะหน้า **วันนี้**; หน้าบันทึกเวลาใช้การรีเฟรชโดยเจตนาของผู้ใช้ เพื่อรักษาข้อมูลที่กำลังกรอก.
- คง “เวลาทำงานรายบุคคล” ไว้หน้า วันนี้ในรูปแบบรายการรายคนที่เปิดรายละเอียดเดือนต่อได้ จึงดูภาพรวมและเจาะหาสาเหตุได้จากจุดเดียว.

### รูปแบบที่ควรยึดต่อไป

- หนึ่งเมนู = หนึ่ง workflow หลัก, หนึ่งแถว = หนึ่งพนักงานหรือหนึ่งคำขอ, และหนึ่งปุ่มเด่น = action ที่สำคัญที่สุดของหน้านั้น.
- Dashboard ใช้เป็น **exception-first**: คิวตัดสินใจก่อน รายชื่อทีมถัดมา และสรุปรายบุคคลเป็นส่วนวิเคราะห์ที่เปิดต่อได้.
- หน้าเงินเดือนยึด flow เดียว: ตรวจ timesheet → แก้ร่าง → ล็อกงวด → บันทึกจ่าย → ออกเอกสาร. ห้ามเปิด action ข้ามสถานะ.

## ปรับ Information Architecture — Dashboard และจุดเช็กอิน

- เปลี่ยนชื่อ route หลักจาก **วันนี้** เป็น **Dashboard** เพื่อสื่อว่าเป็นศูนย์ควบคุม ไม่ใช่หน้าบันทึกเวลาเฉพาะวัน.
- ย้าย **จุดเช็กอินที่อนุญาต** ไปไว้ใต้สรุปรายบุคคลบน Dashboard เพราะเป็นนโยบายการปฏิบัติงานที่ผู้ดูแลต้องเห็นพร้อมสถานะทีม.
- หน้า **บันทึกเวลา** เหลือเพียงการบันทึก/ตรวจรายการเวลาแทน ลดการปนกันของ policy และ write action.
- ตารางจุดเช็กอินคง action เดิมครบ: เพิ่ม, แก้ไข, เปิด/ปิดใช้, และแสดงชื่อพื้นที่, พิกัด, รัศมี และสถานะ.

Dashboard เดิมบอกเฉพาะสถานะ ณ ขณะนั้น จึงยังไม่ตอบคำถามว่า “ทีมเป็นอย่างไรตลอดเดือน และวันใดต้องย้อนตรวจ”. เพิ่มปฏิทินทีมเป็นส่วนหลักหลังสรุปสถานะ โดยมีหลักการดังนี้:

- แต่ละวันสรุปจากข้อมูลลงเวลาเต็มวัน, กำลังทำงาน, และรายชื่อที่ยังต้องตรวจ
- จำนวน “ต้องตรวจ” หักพนักงานที่ได้รับอนุมัติลาแล้ว จึงไม่ตีความการลาเป็นขาดงาน
- เลือกเดือนก่อน/ถัดไปได้ และกดวันที่เพื่อเปิดรายชื่อทีมของวันนั้น
- จากรายชื่อรายวัน กดพนักงานเพื่อเข้าปฏิทินรายบุคคล หรือกดบันทึกเวลาแทนสำหรับวันปัจจุบัน
- อนาคตและวันหยุดอยู่ในสีรอง ส่วนวันที่มีข้อยกเว้นเป็นสถานะสีอำพันเพียงจุดเดียว เพื่อให้ปฏิทินอ่านง่ายในหนึ่งมอง

## HR Command Center — Dashboard redesign

Dashboard ได้รับการออกแบบใหม่จากมุมผู้ดูแลฝ่ายบุคคล โดยไม่ยึดหน้าตาเดิม:

- **ชั้นแรก:** จำนวนกำลังคนที่กำลังทำงานเทียบจำนวนทีม, คนที่ยังไม่มีเวลาเข้า, การเข้าสาย และกะงานที่ใช้อยู่
- **ชั้นที่สอง:** สรุป “เริ่มงานแล้ว / รออนุมัติ / ต้องตรวจเวลา” เป็นปุ่มทางลัดที่มีผลต่อการทำงานจริง
- **ชั้นที่สาม:** คิวตัดสินใจคู่กับทะเบียนทีม เพื่อให้ HR เห็นสิ่งที่ต้องทำและบุคคลที่ได้รับผลกระทบในหน้าจอเดียว
- **หลักฐานและวิเคราะห์:** ปฏิทินทีมเป็นพื้นที่เด่นสำหรับดูทั้งเดือน, แล้วจึงเป็นแนวโน้มรายบุคคล
- **นโยบาย:** จุดเช็กอินที่อนุญาตอยู่ล่างสุดในฐานะการตั้งค่าการปฏิบัติงาน ไม่แข่งขันกับการตัดสินใจรายวัน

สี navy ใช้เฉพาะ moment หลักของกำลังคน, อำพันใช้เฉพาะงานต้องติดตาม, และสีแดงสงวนไว้กับความผิดปกติ. ไม่มีกราฟหรือ card ที่ไม่มี action ต่อ.

### ข้อวิจารณ์ด้านเงินเดือนและสิ่งที่แก้

Dashboard เวอร์ชันก่อนยังบังคับให้ HR จำเองว่าต้องไปหน้าใดต่อหลังพบเวลาไม่ครบ จึงเสี่ยงเปิดพรีวิวเงินเดือนก่อนข้อมูลพร้อม และไม่เห็นความต่างระหว่าง “ตรวจร่าง”, “ล็อกงวด”, “บันทึกจ่าย” กับ “ออกเอกสาร”.

- เพิ่มแถบ **ความพร้อมเงินเดือน** ที่ใช้ข้อมูล summary เดียวกับ workflow การเงิน: งวดที่กำลังตรวจ, จำนวนคนคำนวณได้, ยอดสุทธิประมาณการ และจำนวนเวลาไม่ครบ
- แถบนี้มีสอง action ที่ตรงลำดับงาน: **ตรวจเวลาเข้า–ออก** และ **เปิดตรวจเงินเดือน**; เมื่อมีงวดจ่ายแล้ว action เอกสารเปลี่ยนเป็น **เอกสารจ่ายเงิน**
- Dashboard ไม่สามารถล็อกงวด, บันทึกจ่าย หรือพิมพ์สลิปโดยตรง เพื่อรักษา control ทางการเงินในหน้าเงินเดือนและป้องกันการข้ามขั้น

## Product redesign redline — ทุกหน้าหลังบ้าน

### คำวิจารณ์ตรงไปตรงมา

ระบบเดิมพยายามทำให้ทุกหน้าดูเป็น dashboard จึงใช้ card, badge และปุ่มย่อยมากเกินไป แต่ผู้ใช้ต้องการทำงานให้จบ ไม่ใช่อ่านรายงานหลายชั้น. ปัญหาที่ต้องเลิกใช้คือ: มีหลายหน้าอธิบายเรื่องเดียวกัน, action สำคัญถูกกลืนอยู่ในตาราง, และหน้าการเงินให้ผู้ใช้จำรหัสพนักงานเอง. หน้าจอใหม่ต้องทำหน้าที่เป็น **workbench**: เห็นข้อยกเว้น → เปิดหลักฐาน → ทำ action ที่ถูกสิทธิ์ → กลับมาที่รายการเดิม.

### โครงสร้างผลิตภัณฑ์ใหม่

| กลุ่มงาน | หน้าหลัก | คำถามที่หน้าต้องตอบ | Action เด่นเพียงหนึ่ง |
| --- | --- | --- | --- |
| ควบคุมงาน | Dashboard | วันนี้ใครขาด, สาย, ยังไม่เช็กอิน, และอะไรค้างตัดสินใจ | ตรวจรายการที่ผิดปกติ |
| เวลา | บันทึกเวลา | เวลาใดขาดหรือผิด และใครต้องลงเวลาแทน | บันทึกเวลาแทน |
| บุคคล | บุคคล & อนุมัติ | ข้อมูลใครไม่ครบ และคำขอใดมีผลต่อทีม/เงินเดือน | เพิ่มพนักงาน หรืออนุมัติรายการแรก |
| เงิน | เงินเดือน | งวดใดพร้อม, อะไรบล็อก, จ่ายแล้วหรือยัง | ตรวจงวด / ล็อกงวดตามสถานะ |
| เงิน | เงินล่วงหน้า | เงินใดรออนุมัติ, รอจ่าย, และจะหักงวดใด | ดำเนินรายการถัดไป |
| เงิน | ค่าจ้างและ OT | กติกาใดเป็นนโยบายบริษัท และใครยังไม่มีเรต | ตั้งเรตที่ขาด |
| เอกสาร | ใบแจ้งหนี้ลูกค้า | เอกสารใดรอส่ง, เกินกำหนด, หรือรับชำระแล้ว | ออกใบแจ้งหนี้ |
| ระบบ | ตั้งค่าระบบ | ข้อมูลบริษัท, นโยบาย, ความปลอดภัย, หรือการเก็บข้อมูลอยู่ที่ใด | บันทึกการตั้งค่ากลุ่มนั้น |

### มาตรฐานหน้าจอที่ต้องใช้ร่วมกัน

1. Header บอก **บริบท + ผลกระทบ + action ถัดไป** ไม่ใช้ข้อความการตลาดหรือสถิติลอยๆ.
2. ตารางเป็นตัวหลักสำหรับ HR/การเงิน; card ใช้เฉพาะสถานะสรุป 3–4 ตัวที่กดไปดูรายการจริงได้.
3. สี navy คือ action หรือยอดยืนยันแล้ว, amber คือรอตรวจ, red ใช้เฉพาะข้อผิดพลาด/ความเสี่ยง, ส่วนสีอื่นเป็น neutral.
4. หนึ่งแถวต้องเปิดรายละเอียดได้ และไม่มีการบังคับจำรหัส, คัดลอกรหัส หรือใช้ prompt เพื่อเลือกข้อมูล.
5. การแก้ไขข้อมูลเงินต้องเห็นผลกระทบต่อยอดสุทธิหรือรอบที่จะหักก่อนบันทึกเสมอ.

### Redesign รายหน้า

#### Dashboard

- **ตัด:** dashboard KPI ที่กดต่อไม่ได้, กราฟ decorative และรายชื่อพนักงานแบบ card ใหญ่.
- **ใช้:** แถบกำลังคนวันนี้ → คิวงานที่ต้องตัดสินใจ → ทะเบียนทีมขนาดกะทัดรัด → ปฏิทินทีม → ความพร้อมเงินเดือน.
- **ผลลัพธ์:** HR เปิดหน้าเดียวแล้วรู้ว่าอะไรเสี่ยงต่อการจ่ายเงินเดือนและกดไปยังหลักฐานได้ทันที.

#### บันทึกเวลา

- **ตัด:** การปนจุดเช็กอิน, สรุปรายคน และการตั้งค่านโยบายในจอ write action.
- **ใช้:** ตัวเลือกพนักงาน/วันที่, เวลาเข้า–ออก, เหตุผล, หลักฐานรายการล่าสุด และปุ่มบันทึกเดียว. จุดเช็กอินอยู่ Dashboard ในฐานะ policy.
- **ผลลัพธ์:** แอดมินแก้เวลาได้โดยไม่ถูกเบี่ยงด้วยข้อมูลอื่น และไม่มี refresh อัตโนมัติระหว่างกรอก.

#### บุคคล & อนุมัติ

- **ตัด:** เมนู “พนักงาน” และ “งานรออนุมัติ” ซ้ำกัน.
- **ใช้:** ทะเบียนพนักงานเป็นตารางหลัก; ด้านขวาเป็นคิวลา/OT/เงินล่วงหน้าที่แสดงผลกระทบก่อนอนุมัติ. เปิด profile เป็น drawer เดียวสำหรับข้อมูล, ปฏิทิน, เรต และ completeness.
- **ผลลัพธ์:** เพิ่มคน, ตรวจเอกสาร และอนุมัติงานได้จากบริบทเดียว โดยไม่ทำให้รายชื่อกลายเป็นบัตรขนาดใหญ่.

#### เงินเดือน

- **ตัด:** คำว่า preview/draft/print ที่แข่งขันกัน และการออกเอกสารด้วยการพิมพ์ BVN-XXXX.
- **ใช้:** stepper คงที่: ตรวจ Timesheet → แก้ต้นทาง → ตรวจยอด → ล็อกงวด → บันทึกจ่าย → เอกสารจ่ายเงินรายคน. งวดจ่ายแล้วแสดงปุ่ม “ออกเอกสารจ่าย” ในแถวพนักงานทันที.
- **ผลลัพธ์:** แยกอย่างชัดเจนระหว่างยอดประมาณการ, snapshot ที่ล็อก, เงินที่จ่ายจริง และเอกสารทางการ.

#### เงินล่วงหน้า

- **ตัด:** ลิสต์คำขอที่ไม่บอกว่าจะกระทบงวดใด.
- **ใช้:** ledger หนึ่งแถวต่อรายการ พร้อมสถานะ รออนุมัติ → รอจ่าย → จ่ายแล้ว → หักแล้ว, ยอดคงเหลือ และงวดหักคืน.
- **ผลลัพธ์:** ฝ่ายการเงินไม่ต้องตามยอดจากหลายหน้า และ payroll เห็นที่มาของยอดหัก.

#### ค่าจ้างและ OT

- **ตัด:** ฟอร์มที่ปน rate ของคนกับกติกาทั้งบริษัท.
- **ใช้:** ส่วนแรกเป็น employee pay rule และเตือน “คนที่ยังไม่มีเรต”; ส่วนสองเป็น company policy เช่น OT, วันพิเศษ, ประกันสังคม พร้อมบรรทัดตัวอย่างผลลัพธ์.
- **ผลลัพธ์:** ลดโอกาสตั้งกติกาซ้ำหรือเข้าใจว่า OT ที่ยังไม่อนุมัติถูกจ่ายแล้ว.

#### ใบแจ้งหนี้ลูกค้า

- **ตัด:** การให้ผู้ใช้ค้นหาโลโก้/ข้อมูลบริษัทใน Settings ก่อนออกเอกสาร.
- **ใช้:** invoice ledger แบ่ง ร่าง/ส่งแล้ว/เกินกำหนด/รับชำระแล้ว, มี document preview และหัวบิลที่แก้ได้จากบริบทเดียว.
- **ผลลัพธ์:** งานเอกสารมีสถานะชัด ไม่ปนกับ payroll และลดงานย้อนกลับไปตั้งค่า.

#### ตั้งค่าระบบ และบันทึกการใช้งาน

- **ตัด:** หน้าตั้งค่าที่ยาวต่อเนื่องและมี destructive action อยู่ใกล้การตั้งค่าทั่วไป.
- **ใช้:** กลุ่ม บริษัทและเอกสาร / เวลางานและค่าจ้าง / การเผยแพร่และการเชื่อมต่อ / ความปลอดภัยและข้อมูล. การล้างข้อมูลหรือ archive อยู่ท้ายสุดพร้อม backup status และ two-step confirmation.
- **ผลลัพธ์:** ลดความเสี่ยงการตั้งค่าผิดและทำให้ผู้ใช้พบประกันสังคม/โลโก้/นโยบาย retention ได้จากชื่อกลุ่ม.

### สิ่งที่ทำในรอบนี้

- ปรับภาษาของทุก route ให้บอก outcome ของงานแทนคำกว้างๆ.
- เปลี่ยนงวดที่จ่ายแล้วให้เปิด **เอกสารจ่ายเงินจากแถวชื่อพนักงาน**; ไม่ต้องพิมพ์หรือจำรหัสพนักงานอีก.
- คง control ทางการเงิน: หากยังไม่บันทึกการจ่าย จะยังไม่มีปุ่มออกเอกสาร; Dashboard ไม่สามารถข้ามขั้นล็อกหรือจ่ายเงินได้.

### ลำดับทำต่อที่แนะนำ

1. ทำ employee profile drawer และ advance ledger ให้ครบ เพราะลดจำนวนการเปิดหน้าสลับมากที่สุด.
2. เปลี่ยน Payroll history เป็น batch list ที่เห็น lock/payment/document counts โดยไม่ต้องเปิด modal ก่อน.
3. แยก Settings เป็น four sections ตาม blueprint และนำ audit trail ไปอยู่ในกลุ่ม Security/Data แทนเมนูหลัก.
4. ทำ authenticated UAT ด้วยพนักงานทดสอบ 5 คน, 2 จุดเช็กอิน, OT รออนุมัติ 1 รายการ, เงินล่วงหน้า 1 รายการ และหนึ่งงวดจ่ายจริงจำลองก่อนใช้งานจริง.
